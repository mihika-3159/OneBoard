# Batch M: database, storage and data lifecycle (92–102)

## Portable archives
Owner-only API and Settings UI create a consistent, secret-excluding logical archive. The capture is one transaction (PostgreSQL repeatable read, local SQLite immediate transaction), signed manifest and immutable pages, 200,000 rows / 256 MiB / 4,000 pages; each page is at most 8 MiB. The server retains one export and one staged import per tenant for two days; download and upload resume by page number. No truncation. Capture itself is atomic rather than resumable after a process crash. The archive includes application content and provenance but excludes accounts, authentication state, credentials, derived vectors, transient leases and provider authorizations. Exported content is sensitive; store securely.

The default signing key is domain-separated from AUTH_SECRET_KEY; operators may set PORTABLE_ARCHIVE_SIGNING_KEY to a separately generated base64 32-byte key to preserve verification across deployment/signing-key changes. Never commit that key. Restoration verifies signature, tenant identity, complete ordered manifest, page lengths and SHA-256 digests. It merges missing application rows into the original workspace with matching business profile; existing differing records fail the entire transaction. Account ownership and access state remain unchanged. Restored schedules, pending actions and agent execution are disabled/cancelled; external actions are never replayed, provider tokens must be reauthorized, memory indexes rebuilt. This is not a cross-tenant cloning tool, not a replacement for encrypted full database backups, and not independently authenticated source data.

## Lifecycle and quotas
Deletion classifies every ORM table as direct tenant ownership, indirect sync history or global coordination. Child references are deleted before parents; counts and an in-transaction zero-remaining check are returned. Existing provider data and backup copies are outside application deletion. New archive pages and samples are also tenant-owned and removed. Retention remains opt-in; old finished sync diagnostics, resolved conflicts and completed draft payloads are redacted while idempotency keys, receipts and financial/security audit history remain. Expired temporary archives, OAuth authorization attempts, resource windows and challenge material are cleaned automatically. Global login throttle cleanup acquires the same hashed advisory lock as authentication; stale leases are cleared only when the execution and claim locks can be acquired. Per-category row quotas cover major growing application collections. ORM admission is guarded under tenant locks, portable bulk restore checks the same quotas. Raw SQL or maintenance-owner writes are outside application admission.

## Resource and performance
Per-process PostgreSQL pool size/overflow/timeouts/recycle are bounded; scheduler concurrency respects pool capacity. Tenant/keyset indexes support signed tenant/collection-bound cursors across growing collections. Existing API shapes stay compatible; the new /api/data/collections/{collection} endpoint is keyset-paginated, not a historical snapshot. Dashboard aggregates avoid repeated per-invoice settlement queries and fetching complete task/goal objects. Bounded hourly tenant read probes persist a rolling 1,000-sample history and flag latest latency over max(50ms, 3x prior median). Diagnostics exposes samples and quotas, not SQL or other tenant data. This is a local regression signal, not a production load certification.

## Verification
Mandatory tests exercise signed pages above the old 32 MiB/20,000-row limits, tamper rejection, atomic conflict rollback, resumable upload/download, inactive restored credentials, tenant-bound cursors, quota admission, retention tombstones, expiry cleanup, and ownership deletion. PostgreSQL CI additionally checks populated migration, restricted tenant isolation and concurrent quota admission. Real browser tests verify portable archive controls. All tests use synthetic fixtures.
