# Batch I: workflow automation and execution

Requirements 40–54. The workflow engine uses an allowlisted transaction-only local draft intent. Each step result and its outbox write commit together, protected by a unique tenant/run/step key. Future effects must be explicitly registered and transactional; unregistered tools fail closed. No external send adapter is enabled. An approval carries resolved inputs, exact draft preview, graph digest and run identity; its digest is independently stored in the run checkpoint, and inputs and revision are revalidated before dispatch. Old incomplete approvals cannot be resumed. Cancellation fences further steps and cancels pending local intents; previously processed effects are not reversed. Recovery requires a paused or failed run with the new checkpoint protocol and unchanged active revision; at most two recovery attempts. Rejected or unresolved approvals cannot be bypassed. Successful checkpoints are never replayed.

Opt-in triggers: new customers (CSV commit plus bounded detection of other new recorded customers), sent/overdue past-due invoices (dedup by invoice ID and due date), threshold crossings on valid recorded financial metrics, and authenticated write-capable founder API-key webhooks. Creation alone does not enable event detection: save an active definition explicitly. POST /api/workflows/{workflow_id}/webhook with event_id (8–200 chars) and payload (8 KiB cap); repeat identity plus same payload returns the same queue record, changed payload fails. Do not include credentials in event payloads. Queue is tenant-scoped, pinned to revision, uses durable lease and stable execution identity; 3 automatic attempts plus one operator retry if no run exists. Dead letters linked to committed runs require run recovery, not duplicate dispatch. Retained replay tombstones count toward the 10,000-record tenant limit; quota failure is visible and never silently drops accepted events.

Editor creates immutable revision snapshots with optimistic concurrency. Restore creates a new inactive revision, not an overwrite. Saving a new revision suspends prior schedules and invalidates existing approval/queued event identities. Legacy workflows start at revision 1 on first edit. Conditional node operators eq/ne/gt/gte/lt/lte use scalar literals or ancestor result bindings, e.g. {"operator":"gt","right":10,"bindings":{"left":{"step":"start","field":"event.value"}}}; boolean branch edges activate the matching path and joins run when an incoming active path succeeds. No dynamic code execution. Browser execution identities persist in local storage until a durable run is returned. Run and event histories display failure, recovery, approval and dead-letter status and refresh while open.

Schedules accept five fields, explicit named weekdays (mon..sun), monthly/yearly date selectors, lists/ranges and interval syntax with minimum five-minute frequency. DST nonexistent times skip; repeated wall times execute once. Policies: coalesce missed slots, skip missed slots, or catch up one oldest slot per pass. Pending approval, uncertain/failed/cancelled run pauses the schedule. Four independent tenant workers in production, bounded tenant cursor and per-tenant schedule/event dispatch limits. This is not a measured unlimited-throughput guarantee. Existing runtime grants must be refreshed by the approved provisioning procedure after migration 020. All real external delivery remains disabled until a separately authorized adapter is implemented.

Acceptance: mandatory backend, PostgreSQL migration/concurrency/restore, browser, Windows, and existing live inference CI on the exact head. No Batch J work.
